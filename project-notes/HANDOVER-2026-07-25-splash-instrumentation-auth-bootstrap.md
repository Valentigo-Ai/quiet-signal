1. **Splash-dismiss instrumentation + a real timing bug fix.** The app was reported hanging on a plain navy screen on cold start, requiring a force-close — separate from (and after) the auth-bootstrap hang fixed and confirmed the day before (commit `0fcf4ea2`). Both `SplashScreen.hideAsync()` call sites (`RootNavigator.tsx`'s `onReady`, `App.tsx`'s failsafe timer) previously swallowed all errors silently with `.catch(() => {})` — zero telemetry if it ever failed again. Added `reportSplashHideFailure(err, callSite)` and a `logSplashOnReady()` breadcrumb in `sentry.ts`, following the existing `reportStartupHang` convention. While investigating, found and fixed a real (if narrow) bug: the splash-hide failsafe fired at 8s, but `AuthContext`'s bootstrap could legitimately take up to ~10s worst case (6s `getSession` timeout + 4s consent-check timeout, sequential) — so the failsafe could hide the splash while `RootNavigator` was still rendering `null`, and since the splash background, `app.json`'s root `backgroundColor`, and `RootNavigator`'s blank state are all the same navy (`#0B1128`), that read as "still hung" even though it wasn't. Bumped the failsafe to 12s. Commit `d577c87a`.
2. **Auth-bootstrap was too aggressive about signing users out.** The `withTimeout` race added the day before (commit `0fcf4ea2`) fixed the *hang* but over-corrected: on a 6s timeout it called `setSession(null)`, treating "the network refresh is slow" identically to "genuinely not authenticated." In production, with the default 1hr Supabase access-token expiry, this meant: reopen the app after the token's expired, refresh takes >6s, get dropped to the login screen and have to retype credentials — even though the refresh token was perfectly valid. Real churn risk for a mental-health app. Fixed by separating "slow" from "actually invalid": added `getPersistedSession()` to `supabase.ts` (reads the session AsyncStorage persists directly — key `sb-<project-ref>-auth-token` — without ever touching the network), and restructured `AuthContext.tsx`'s bootstrap so that if a persisted session exists (even expired), it's used optimistically to let the user straight into the app while the real `getSession()` keeps running in the background. `setSession(null)` now only happens when gotrue-js itself resolves a genuine, conclusive failure (confirmed via reading `node_modules/@supabase/auth-js` source: `__loadSession` only ever returns `session: null` for a decided outcome — nothing persisted, or a refresh that actually, terminally failed — never merely because it's slow) — never off our own clock. A 45s hard-timeout is the last-resort fallback if the background call never settles at all (permanently offline device), forcing sign-out so there's still a recovery path. No-persisted-session cold starts (brand new device) are unaffected — that path was already fast (no network call happens at all when storage is empty). `reportStartupHang` in `sentry.ts` gained an optional `outcome` tag (`"slow" | "timeout-fallback" | "background-error"`) so Sentry can tell these apart; existing call sites unaffected. Commit `89e3c24f`.

Both fixes are **instrumentation + a genuine narrow-case fix**, not a confirmed root-cause fix for the original navy-screen hang — there is still no real Sentry event showing what actually causes the hang when it's worse than the ~10-12s window these fixes cover. That requires the shipped build to actually reach a device and the bug to recur (or not) with telemetry now in place.
